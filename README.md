# DeepSeek 喂白饭插件（astrbot_plugin_dsAutoPay）

独立 AstrBot 插件：群友创建 DeepSeek 充值订单、扫描支付二维码，插件后台有限轮询确认支付，提供本人账单查询。

**款项进入管理员配置的 DeepSeek 账户，不是群友自己的 DeepSeek 账户。** 插件负责创建支付二维码、确认 DeepSeek 充值结果和查询本人订单。

## 安装

需要 Python 3.11+、当前 AstrBot 4.x 和 NapCat / OneBot v11。将完整目录放到 `AstrBot/data/plugins/astrbot_plugin_dsAutoPay`，在 AstrBot Python 环境安装依赖：

```sh
python -m pip install -r requirements.txt
```

在 AstrBot WebUI 加载插件、填写配置、保存并重载。已通过一次真实的 1 元支付宝创建订单、二维码扫码支付与查单确认验证；尚未在真实 AstrBot + NapCat 环境完成群内发码和通知联调。离线测试使用 HTTP 与框架替身，不会产生付款或充值订单。

数据库保存在 `data/plugin_data/astrbot_plugin_dsAutoPay/orders.sqlite3`。插件代码目录不保存登录凭证、二维码图片或运行数据库。二维码在内存中生成。

## 配置

管理员配置只保留 `web_token` 和 `allowed_groups`，不再提供 Cookie、设备字段或账户别名输入项。2026-10-23 实测仅携带 Bearer 认证和 order_info，成功创建了一笔 1 元支付宝待支付订单，未付款；未携带 Cookie、设备值或自定义 x-client 请求头。这是当前会话的验证结果，微信最小字段组合尚未单独实测。订单金额、渠道、币种、request_id 均由插件生成，不需管理员逐笔配置。

| 配置项 | 含义 |
| --- | --- |
| `web_token` | DeepSeek 开放平台（platform.deepseek.com）请求 Authorization 中 Bearer 后面的登录令牌，**不是模型 API Key** |
| `allowed_groups` | 允许发起充值的 QQ 群号；空列表关闭群服务 |

凭证只通过管理员的插件配置填写，不在群里发送，不提交 Git。仓库不包含之前聊天里的任何真实凭证。DeepSeek 开放平台网页登录认证可能过期；HTTP 401/403 会暂停该插件实例的网络查询，日志提示管理员更新配置并重载。业务错误码未建立完整映射，其他错误按退避处理。

当前为单 DeepSeek 账户插件，账户命名空间由插件内部管理，兼容已有配置中的旧别名。更新同一账户的登录令牌不影响历史订单；不能在同一数据目录直接替换为另一个 DeepSeek 账户的令牌。若要更换收款账户，先处理旧订单并停服备份，再使用独立数据目录部署；本插件尚不能自动识别上游用户 ID。仅支持一个插件实例使用该数据库。

## 用户命令

金额由用户自定义，只能充值整数，范围为 1 至 100000 元（含边界），例如 `/微信喂白饭 6元`、`/支付宝喂白饭 12元`。不限制固定档位；旧配置中的 `amounts` 不再使用。DeepSeek 上游实际金额限制仍以接口响应为准。

“喂白饭”即给 DeepSeek 账户充值。原 `/充值`、`/微信支付充值`、`/支付宝充值` 等旧入口已更名，不再注册。

| 命令 | 功能 |
| --- | --- |
| `/喂白饭` | 显示支付方式选择提示，不创建订单 |
| `/微信喂白饭 20元` | 创建微信支付订单，在原群 @本人并发送二维码 |
| `/支付宝喂白饭 20元` | 创建支付宝订单，在原群 @本人并发送二维码 |
| `/喂白饭账单` | 最近五笔本人订单 |
| `/喂白饭账单 2` | 本人账单第二页 |
| `/喂白饭查询` | 查询本人最近一笔订单 |
| `/喂白饭查询 DS完整订单号` | 主动核对指定的本人订单 |

充值只能在开放群发起；本人账单和主动查单也可私聊机器人。所有命令都以消息发送人的 QQ 为身份，**不能传别人的 QQ 查账**。即便猜到他人的订单号，也无法读取或触发查询。DeepSeek 历史订单中没有本地 QQ 绑定的记录不会展示，赠送记录不会当成用户充值。

在群里查询时，回复自然对群成员可见；要避免展示自己的订单金额，请私聊查询。

每人同一时刻只创建一张仍在 15 分钟有效期内的待支付二维码。重复消息或重复申请会返回已有订单信息，不会重复创建或重新发码。创建命令有 60 秒冷却；同一账户最多 100 笔自动处理中订单。

二维码消息只发送一次，说明“请在 15 分钟内完成支付”；不更新倒计时、不催付、不通知过期或取消。查到已支付后在原群 @申请人发送成功通知。若首次二维码消息发送失败，请联系管理员核对，不要盲目重复充值。

## 支付渠道

两种方式使用浏览器提供的实际参数：

| 指令 | payment_method_type | fallback_method_type |
| --- | --- | --- |
| `/微信喂白饭` | CMB_UNIONPAY | WECHAT |
| `/支付宝喂白饭` | CMB_UNIONPAY | ALIPAY |

二维码提示随用户选择显示“请使用微信扫码”或“请使用支付宝扫码”。上游均按银联主渠道、对应备用渠道请求；这不是保证二维码在支付网络中只能被某一种 App 扫描。若实际扫码渠道与选择不同，仍以正确订单的成功支付为准，并分别记录选择方式与实际渠道。

旧版订单平滑增加渠道字段，选择方式按原创建参数记为支付宝；上游返回的实际渠道单独保存。仍保持每人一张有效待支付二维码：切换方式时若已有未结束订单，会提示先处理原订单，不把旧二维码冒充成新渠道二维码。15 分钟过后可重新选择方式申请新订单。

## 状态与轮询

| 本地状态 | 含义 |
| --- | --- |
| `CREATING` | 正在创建上游订单 |
| `PENDING` | 未支付，对应上游 CREATED |
| `PAID` | 已确认 DeepSeek 支付成功，为本插件终态 |
| `FAILED` | 上游返回 FAILED |
| `EXPIRED` | 创建满 15 分钟，尚未确认支付；不是认定上游已取消 |
| `REVIEW_REQUIRED` | 创建结果不明、金额/币种不符、未知状态或支付时间异常，需人工核对 |

只有同一 `payment_order_id`、相同人民币金额、`currency=CNY`、`payment_order_status=SUCCESS` 且有格式有效的带时区 `paid_at`，才转为 PAID。成功后不会被旧状态覆盖。

后台共享一个查询任务：

- 有订单到查询时间才调用一次列表接口，批量匹配所有到期订单，不按每个群友各请求一次。
- 0～15 分钟：每 10 秒查询。第 15 分钟的到期查询后，在第 16、20、30 分钟补查，随后停止自动查询。
- FAILED 不发通知；因终态语义未完全验证，仍在上述有限窗口内补查。PAID 和 REVIEW_REQUIRED 停止自动查单。
- 接口暂时失败时退避 20、40、80、160、300 秒，且不把网络错误改成支付失败。到达最终补查时仍失败，也结束自动查询。
- 主动查单每个 QQ 30 秒一次，全部请求共享至少 10 秒的网络查询间隔；处于全局冷却时返回本地最近结果。主动查单可在自动查询停止后确认迟到支付，但不会为订单重开无限轮询。
- 重启恢复未完成订单；若重启时已超过 30 分钟，对尚未完成自动查询的订单做一次最终核对后结束。CREATING 状态转待核对，绝不自动重复 POST。

15 分钟来自实际使用反馈，并非创建接口返回的到期字段。页面“已取消”与 CREATED 可能同时存在，不能根据 UI 字样或本地时间判定付款成功/失败。

支付成功通知采用最多三次发送尝试，失败间隔 60 秒；成功标记落库后不再发送。若进程恰好在 QQ 已发送、数据库尚未记通知成功之间崩溃，恢复后可能重复通知；支付订单状态不会重复确认或增加任何余额。通知全部失败仍可通过本人账单看到已支付。

## 边界与运维

- 这两条接口是 DeepSeek 网页内部接口，不是官方公开承诺稳定的支付 API。字段、认证、限流或页面逻辑变化可能需要适配。
- 创建超时有可能已经生成订单，所以本地保留待核对记录，不自动重发 POST。没有返回上游订单号时，无法安全地凭相同金额匹配到账，需要管理员在 DeepSeek 后台核对。
- 当前不支持退款、管理员替用户确认成功或账单导出。金额异常及需要核对的订单，必须先在上游查明原因。
- 相同金额的不同订单仅凭订单号区分，不能用账户余额增加量判断是谁付款。
- 列表接口是否存在隐式条数限制、记录保留窗口或分页尚未确定，未找到订单不等于没有付款。
- 停服备份整个插件数据目录；不要仅热拷贝 SQLite 主文件而遗漏 WAL。若配置令牌失效，既有订单不会丢失。

接口样本及验证依据见 [DeepSeek 支付接口记录](docs/deepseek-payment-api.md)。

### 自动生成的 request_id

`request_id` 是插件每次创建支付订单时生成并保存的 UUID 请求编号，不需要管理员或群友填写。它不同于服务端返回的 `payment_order_id`，也不是 QQ 或 DeepSeek 用户 ID。查单匹配使用 `payment_order_id`。上游是否将 request_id 用于幂等处理尚未验证，所以不能仅靠重复使用它就自动重试创建请求。
